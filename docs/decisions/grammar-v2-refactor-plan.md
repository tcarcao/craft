# Craft Grammar v2 — Refactor Implementation Plan

Status: **Ready to implement**. Produced from the grill-me design session on 2026-04-21. All design questions are resolved; this document is self-contained and can be executed by another agent without re-opening design debate.

---

## 1. Goals

Improve `craft/tools/antlr-grammar/Craft.g4` to:

1. Be more pleasant to **write** (primary).
2. Be more predictable to **parse** (no silent ambiguity resolutions).
3. Be more pleasant to **maintain** (less `NEWLINE*` noise, less keyword-injection sprawl).

Breaking changes are permitted. The existing example corpus under `craft/examples/` MUST still parse after the refactor — it's the compatibility target.

## 3. Design decisions (frozen)

| ID | Decision | Breaking |
|---|---|---|
| Q1 | `asks`, `notifies`, `returns`, `listens` are **hard-reserved**. They cannot appear in `identifier`. | Yes |
| Q2 | `returns` takes `to <target>?`. The token immediately after `returns to` is **always** the target domain. The infinitive sense of "to" (e.g. "returns to finalize") is not supported — rephrase as two actions. Bare `returns <phrase>` is legal and means "return to the implicit caller from the enclosing trigger". | Yes for files using `returns to <verb>` as infinitive |
| Q3 | `NEWLINE` is significant **only inside `use_case` bodies** (scenarios, actions). Everywhere else (services, domains, arch, exposures, actors, top-level) newlines are whitespace. | No (strictly more permissive) |
| Q4 | Structural keywords (`arch`, `services`, `service`, `domain`, `domains`, `actor`, `actors`, `use_case`, `when`, `exposure`, `presentation`, `gateway`, `to`, `through`, `contexts`, `data-stores`, `language`, `deployment`) are **hard-reserved** and removed from `identifier`. Connector words (`a`, `an`, `the`, `as`, `to`, `from`, `in`, `on`, `at`, `for`, `with`, `by`, `of`) and type-value words (`user`, `system`, `service`, `canary`, `blue_green`, `rolling`) stay injectable into `identifier` so phrases flow naturally. | Yes for identifiers that collide with a structural keyword |
| Q5 | `actorType` → any `IDENTIFIER`. Open taxonomy. | No |
| Q6 | `deployment_type` → any `IDENTIFIER`. Open taxonomy. | No |
| Q7 | `modifier_value` accepts `IDENTIFIER \| STRING \| number`. (`number` is a new token supporting optional decimal.) | No |
| Q8 | Block comments `/* ... */` added. | No |
| Q9 | `IDENTIFIER` character class unchanged: `[a-zA-Z0-9_][a-zA-Z0-9_.-]*`. | No |
| Q10 | `STRING` gains escape sequences: `\"`, `\\`, `\n`, `\t`, `\r`. | No |
| Q11 | Keep both singular (`service X { }`) and grouped (`services { X { } }`) forms. Factor shared rule fragments internally. | No |
| Q12 | Keep the subject-less trigger form: `when <quoted_event>`. | No |
| Q13 | Actor vs domain remain syntactically identical (`identifier`); distinguish at the semantic/validation layer only. | No |
| Q14 | No grammar-level imports. Tooling globs all `.craft` in a folder as one logical model (already the pattern — verify). | No |

## 4. Target grammar (Craft.g4)

The grammar below is the **target state**. It is written in conventional ANTLR4 style. Rename existing rule tokens only where indicated; otherwise preserve names so downstream visitor code breakage is minimized.

```antlr
grammar Craft;

// =============================================================================
// Parser rules
// =============================================================================

dsl
    : top_level_item* EOF
    ;

top_level_item
    : arch
    | services_def
    | service_def
    | domain_def
    | domains_def
    | actors_def
    | actor_def
    | exposure
    | use_case
    ;

// ---------- Domain ----------------------------------------------------------

domain_def
    : DOMAIN domain_name '{' bounded_context* '}'
    ;

domains_def
    : DOMAINS '{' domain_block* '}'
    ;

domain_block
    : domain_name '{' bounded_context* '}'
    ;

domain_name       : IDENTIFIER ;
bounded_context   : IDENTIFIER ;

// ---------- Actors ----------------------------------------------------------

actor_def
    : ACTOR actor_type actor_name
    ;

actors_def
    : ACTORS '{' actor_definition* '}'
    ;

actor_definition
    : actor_type actor_name
    ;

// Q5: open — any identifier. Tooling decides the known set.
actor_type : IDENTIFIER ;
actor_name : IDENTIFIER ;

// ---------- Architecture ----------------------------------------------------

arch
    : ARCH arch_name? '{' arch_section+ '}'
    ;

arch_name : IDENTIFIER ;

arch_section
    : presentation_section
    | gateway_section
    ;

presentation_section
    : PRESENTATION ':' arch_component+
    ;

gateway_section
    : GATEWAY ':' arch_component+
    ;

arch_component
    : component_chain
    ;

component_chain
    : component_with_modifiers ('>' component_with_modifiers)*
    ;

component_with_modifiers
    : component_name component_modifiers?
    ;

component_name : IDENTIFIER ;

component_modifiers
    : '[' modifier_list ']'
    ;

modifier_list
    : modifier (',' modifier)*
    ;

// Q7: modifier values are identifier | STRING | number
modifier
    : modifier_key (':' modifier_value)?
    ;

modifier_key   : IDENTIFIER ;
modifier_value : IDENTIFIER | STRING | NUMBER ;

// ---------- Exposure --------------------------------------------------------

exposure
    : EXPOSURE exposure_name '{' exposure_property+ '}'
    ;

exposure_name : IDENTIFIER ;

exposure_property
    : TO       ':' target_list
    | CONTEXTS ':' context_list
    | THROUGH  ':' gateway_list
    ;

target_list   : IDENTIFIER (',' IDENTIFIER)* ','? ;
context_list  : IDENTIFIER (',' IDENTIFIER)* ','? ;
gateway_list  : IDENTIFIER (',' IDENTIFIER)* ','? ;

// ---------- Services --------------------------------------------------------

service_def
    : SERVICE service_name '{' service_property* '}'
    ;

services_def
    : SERVICES '{' service_block* '}'
    ;

service_block
    : service_name '{' service_property* '}'
    ;

service_name : IDENTIFIER | STRING ;

service_property
    : CONTEXTS    ':' context_list
    | DATA_STORES ':' datastore_list
    | LANGUAGE    ':' IDENTIFIER
    | DEPLOYMENT  ':' deployment_strategy
    ;

datastore_list : IDENTIFIER (',' IDENTIFIER)* ','? ;

// Q6: deployment_type is open
deployment_strategy
    : deployment_type ('(' deployment_config ')')?
    ;

deployment_type : IDENTIFIER ;

deployment_config
    : deployment_rule (',' deployment_rule)*
    ;

deployment_rule
    : PERCENTAGE '->' deployment_target
    ;

deployment_target : IDENTIFIER ;

// ---------- Use cases -------------------------------------------------------
// Newlines ARE significant inside a use_case body (Q3). To scope the sensitivity,
// the lexer pushes into a dedicated mode when a use_case body opens and pops
// when it closes. See lexer section below.

use_case
    : USE_CASE STRING USECASE_OPEN_BRACE NEWLINE* scenario* USECASE_CLOSE_BRACE
    ;

scenario
    : trigger action*
    ;

trigger
    : WHEN domain_name LISTENS quoted_event NEWLINE+
    | WHEN external_trigger           NEWLINE+
    | WHEN quoted_event               NEWLINE+
    ;

external_trigger
    : actor_ref verb connector_word? phrase?
    ;

action
    : sync_action     NEWLINE+
    | async_action    NEWLINE+
    | return_action   NEWLINE+
    | internal_action NEWLINE+
    ;

sync_action
    : source=domain_name ASKS target=domain_name connector_word? phrase
    ;

async_action
    : domain_name NOTIFIES quoted_event
    ;

// Q2: single-alternative return_action. Target is optional; if omitted, the
// caller is inferred from the enclosing trigger at the semantic layer.
return_action
    : domain_name RETURNS (TO target=domain_name)? connector_word? phrase?
    ;

internal_action
    : domain_name verb connector_word? phrase
    ;

phrase
    : (phrase_word | STRING)+
    ;

// Q4: phrase_word drops the 'when' / 'use_case' re-injection (no longer needed
// because those keywords are no longer in identifier).
phrase_word
    : identifier
    | connector_word
    ;

connector_word
    : A | AN | THE | AS | TO | FROM | IN | ON | AT | FOR | WITH | BY | OF
    ;

actor_ref   : IDENTIFIER ;
verb        : IDENTIFIER ;
quoted_event: STRING ;

// ---------- Identifier ------------------------------------------------------
// Q4: structural keywords are NOT in identifier. Connector and type-value words
// remain injectable so phrases can read naturally.
identifier
    : IDENTIFIER
    // type-value tokens (still usable as names)
    | USER | SYSTEM | SERVICE_KW | CANARY | BLUE_GREEN | ROLLING
    // connector tokens (still usable as names)
    | A | AN | THE | AS | TO | FROM | IN | ON | AT | FOR | WITH | BY | OF
    ;

// =============================================================================
// Lexer rules
// =============================================================================

// ---- Structural keywords (hard-reserved) -----------------------------------

ARCH          : 'arch' ;
SERVICES      : 'services' ;
SERVICE       : 'service' ;
DOMAIN        : 'domain' ;
DOMAINS       : 'domains' ;
ACTOR         : 'actor' ;
ACTORS        : 'actors' ;
USE_CASE      : 'use_case' ;
WHEN          : 'when' ;
EXPOSURE      : 'exposure' ;
PRESENTATION  : 'presentation' ;
GATEWAY       : 'gateway' ;
THROUGH       : 'through' ;
CONTEXTS      : 'contexts' ;
DATA_STORES   : 'data-stores' ;
LANGUAGE      : 'language' ;
DEPLOYMENT    : 'deployment' ;

// ---- Action verbs (hard-reserved, Q1) --------------------------------------

ASKS      : 'asks' ;
NOTIFIES  : 'notifies' ;
RETURNS   : 'returns' ;
LISTENS   : 'listens' ;

// ---- Type-value words (soft; still usable as identifiers via `identifier`) -

USER        : 'user' ;
SYSTEM      : 'system' ;
SERVICE_KW  : 'service' ;   // NOTE: collides with SERVICE above? See §4.1
CANARY      : 'canary' ;
BLUE_GREEN  : 'blue_green' ;
ROLLING     : 'rolling' ;

// ---- Connector words (soft; still usable as identifiers) -------------------

A     : 'a' ;
AN    : 'an' ;
THE   : 'the' ;
AS    : 'as' ;
TO    : 'to' ;
FROM  : 'from' ;
IN    : 'in' ;
ON    : 'on' ;
AT    : 'at' ;
FOR   : 'for' ;
WITH  : 'with' ;
BY    : 'by' ;
OF    : 'of' ;

// ---- Literals --------------------------------------------------------------

PERCENTAGE  : NUMBER '%' ;
NUMBER      : [0-9]+ ('.' [0-9]+)? ;  // Q7 (also enables 99.5% percentages)
IDENTIFIER  : [a-zA-Z0-9_] [a-zA-Z0-9_.-]* ;
STRING      : '"' ( '\\' [ntr"\\] | ~["\\\r\n] )* '"' ;    // Q10 escapes

// ---- Newlines --------------------------------------------------------------

// Outside use_case bodies: newlines are ignored whitespace.
// Inside use_case bodies: newlines are significant tokens.
NEWLINE     : '\r'? '\n' -> channel(HIDDEN) ;

// Lexer mode flipping — see §4.2 for the exact mechanism.

// ---- Whitespace & comments -------------------------------------------------

WS            : [ \t]+             -> skip ;
LINE_COMMENT  : '//' ~[\r\n]*      -> skip ;
BLOCK_COMMENT : '/*' .*? '*/'      -> skip ;   // Q8
```

### 4.1 Token collision: `SERVICE` vs `SERVICE_KW`

ANTLR cannot have two lexer rules matching the same string `'service'`. Resolution: **reuse a single `SERVICE` token** and handle it contextually.

Approach: define only `SERVICE : 'service'` in the lexer. In the parser, the `actor_type` rule and the `service_def` rule both accept the `SERVICE` token; the rule that wins is determined by context (after `actor` keyword → actor_type; otherwise → service_def). Additionally, include `SERVICE` as an alternative in the `identifier` rule so phrase words and domain names can still be the string `service`.

Minimal edit to the grammar snippet above:

- Delete the `SERVICE_KW` lexer rule.
- Everywhere `SERVICE_KW` appears, use `SERVICE` instead.
- The `service_def` rule already uses `SERVICE` as the `'service'` keyword — no ambiguity, since parser context disambiguates.

### 4.2 Newline scoping — three implementation options

The grammar above writes `NEWLINE` into the use_case productions but hides the token globally. Pick ONE of the following to make `NEWLINE` significant only inside `use_case`:

**Option A — Lexer modes (cleanest).** Add a mode that activates on `use_case <STRING> {` and deactivates on the matching `}`. Inside the mode, `NEWLINE` stays on the default channel; outside, `-> channel(HIDDEN)`. Requires token rewrites and a custom `{ }` tracker for nested braces (use_case bodies don't nest, so this is simple).

**Option B — Action-level token mode switch.** In the default channel, define:

```antlr
USECASE_OPEN_BRACE  : '{' { /* custom: mark mode on */ } -> pushMode(USECASE_BODY);
```

Inside `mode USECASE_BODY`:

```antlr
USECASE_CLOSE_BRACE : '}' -> popMode ;
USECASE_NEWLINE     : '\r'? '\n' ;  // significant
// ... replicate identifier, string, keyword rules in the mode,
// or use `channels` to forward them.
```

ANTLR4 lexer modes work but require redeclaring or forwarding rules. This is verbose.

**Option C — Single channel, but custom token filter (recommended for first pass).** Keep `NEWLINE` on the default channel everywhere. Add `NEWLINE*` where needed (basically just the use_case body) and make every other rule that currently references `NEWLINE*` swallow them naturally by accepting any number. This is functionally equivalent to "newlines don't matter outside use_case" because those outer rules become permissive, without requiring a lexer-mode mechanism. **Simplest; zero lexer complexity.**

**Recommendation: Option C.** It achieves Q3's intent (authors can write `services { A{} B{} C{} }` on one line) without lexer-mode surgery. The only rules that need `NEWLINE` are:

- `trigger` (action/trigger separator inside use_case)
- `action` alternatives (each action terminated by `NEWLINE+`)
- `use_case` (to allow a trailing blank line after the body)

Everywhere else, delete the `NEWLINE*` / `NEWLINE+` occurrences entirely — the token won't appear because it's hidden.

Wait — if `NEWLINE` is on `HIDDEN` channel, the parser won't see it at all, including inside `use_case`. To make it visible again in `use_case` without lexer modes, we need a different approach:

**Revised Option C.** Keep `NEWLINE` on the **default channel** (i.e. `-> skip` or hidden is NOT used). Then:

- Inside use_case productions, reference `NEWLINE+` explicitly where scenario/action boundaries are needed.
- Outside use_case productions, allow `NEWLINE*` liberally — i.e. wherever any nonterminal currently appears in a block, wrap it so newlines are absorbed. Concretely, redefine the outer rules with `NEWLINE*` inserted generously, then rely on the fact that these outer rules don't need newlines to terminate anything (they terminate at `}` or at the next keyword).

This is still verbose; to keep it clean, introduce a parser rule:

```antlr
// an "nl" fragment that matches zero or more newlines
nl : NEWLINE* ;
```

and insert `nl` at every spot inside non-use_case blocks where newlines might appear. The resulting grammar reads cleanly:

```antlr
services_def
    : SERVICES '{' nl (service_block nl)* '}' nl
    ;
```

This is the **final chosen approach** for the refactor: one `nl` parser rule + explicit `NEWLINE+` in use_case productions only.

## 5. Tree-sitter grammar (`tree-sitter-craft/grammar.js`)

Mirror every change from §4 with these specific edits:

1. **Hard-reserve action verbs and structural keywords.** The current tree-sitter grammar already uses string literals for the keywords (`'asks'`, `'notifies'`, `'returns'`, `'listens'`, `'when'`, `'arch'`, etc.), so no identifier-re-injection exists in the first place. Confirm by inspection — if so, tree-sitter is already "naturally" enforcing Q1/Q4.
2. **Remove hard-coded actor_type choice**: change `actor_type: $ => choice('user', 'system', 'service')` to `actor_type: $ => $.identifier`.
3. **Remove hard-coded deployment_type choice**: change `deployment_type: $ => choice('canary', 'blue_green', 'rolling')` to `deployment_type: $ => $.identifier`.
4. **Modifier value**: current `modifier_value: $ => choice($.identifier, $.number, $.boolean)` — extend to also allow `$.string`. Drop `$.boolean` since `true` / `false` are already valid identifiers under `$.identifier` (which is `/[a-zA-Z_][a-zA-Z0-9_-]*/`).
5. **Return action**: collapse the two `choice` branches into a single pattern mirroring the ANTLR rule: `source RETURNS (TO target)? connector? phrase?`.
6. **Remove the `'when'`/`'use_case'` re-injection workaround** in phrase: the current tree-sitter `phrase` already doesn't include those. Confirm.
7. **Identifier character class**: current tree-sitter is `/[a-zA-Z_][a-zA-Z0-9_-]*/` — this is **narrower** than the ANTLR `IDENTIFIER`. Decision Q9 keeps ANTLR's character class unchanged (leading digits, dots, hyphens). The tree-sitter grammar is diverged today. Align by changing to `/[a-zA-Z0-9_][a-zA-Z0-9_.-]*/`. Note: this may require escaping/ordering care because tree-sitter and ANTLR have subtly different regex semantics.
8. **String escapes (Q10)**: current tree-sitter already supports `/\\./` — matches the plan.
9. **Block comments (Q8)**: already present in the tree-sitter `comment` rule. No change.
10. **Newline scoping (Q3)**: the tree-sitter grammar currently does NOT skip newlines globally — it explicitly declares `/[ \t]/` as extras, keeping newlines as tokens. To mirror the ANTLR behavior, change `extras` to include `$._newline` — **but** only in non-use_case contexts. Tree-sitter doesn't support "newlines significant in this subtree only" cleanly. Workaround:
    - Add `$._newline` to `extras`. This makes newlines whitespace globally.
    - For use_case body: keep newline sensitivity by using explicit terminators. Either (a) switch to a different separator inside use_case bodies, or (b) accept that tree-sitter's parsing of use_case will be slightly less strict than ANTLR's (the authoritative Go parser remains strict).
    - **Recommended**: go with (b). The tree-sitter grammar is used only for editor syntax highlighting/folding — a looser parse is acceptable. Tree-sitter already runs looser than ANTLR in several places today (see `tree-sitter-craft/grammar.js` `/* ... handled by ANTLR parser */` comments).

## 6. Step-by-step execution plan

Execute in this order. Each phase has a clear exit criterion.

### Phase 0 — Branch and baseline

### Phase 1 — ANTLR grammar refactor (Craft.g4)

Do these edits to `craft/tools/antlr-grammar/Craft.g4` in order:

**1.1 — Lexer consolidation.**

- Promote every structural keyword to its own lexer rule (`ARCH`, `SERVICES`, `SERVICE`, `DOMAIN`, `DOMAINS`, `ACTOR`, `ACTORS`, `USE_CASE`, `WHEN`, `EXPOSURE`, `PRESENTATION`, `GATEWAY`, `TO`, `THROUGH`). `CONTEXTS`, `DATA_STORES`, `LANGUAGE`, `DEPLOYMENT` are already tokens — keep.
- Add `ASKS`, `NOTIFIES`, `RETURNS`, `LISTENS`.
- Add connector tokens: `A`, `AN`, `THE`, `AS`, `FROM`, `IN`, `ON`, `AT`, `FOR`, `WITH`, `BY`, `OF`. (`TO` is already added.)
- Add type-value tokens: `USER`, `SYSTEM`, `CANARY`, `BLUE_GREEN`, `ROLLING`. (`SERVICE` is already there — shared with the structural keyword; see §4.1.)
- Replace `PERCENTAGE: [0-9]+ '%'` with `PERCENTAGE: NUMBER '%'` and add `NUMBER: [0-9]+ ('.' [0-9]+)?`.
- Update `STRING` regex to support escapes: `'"' ( '\\' [ntr"\\] | ~["\\\r\n] )* '"'`.
- Add `BLOCK_COMMENT: '/*' .*? '*/' -> skip`.
- **Critical:** in ANTLR, the token order matters. Lexer rules declared earlier win in case of identical-length matches. Put all fixed-string tokens (keywords) **before** `IDENTIFIER`. Put `NUMBER` before `IDENTIFIER` (otherwise `9service` tokenizes as IDENTIFIER — which is fine — but `99` would tokenize as IDENTIFIER instead of NUMBER).

**1.2 — Introduce `nl` helper rule.** Add `nl : NEWLINE* ;` at the top of the parser rules.

**1.3 — Rewrite `dsl` top-level.**

```antlr
dsl : nl top_level_item* EOF ;
top_level_item : (arch | services_def | service_def | domain_def | domains_def | actors_def | actor_def | exposure | use_case) nl ;
```

**1.4 — Rewrite every non-use_case block** to use `nl` instead of inline `NEWLINE*` / `NEWLINE+`. Example — before:

```
domain_def: 'domain' domain_name '{' NEWLINE* bounded_context_list '}' NEWLINE*;
bounded_context_list: bounded_context (NEWLINE+ bounded_context)* NEWLINE*;
```

After:

```antlr
domain_def : DOMAIN domain_name '{' nl (bounded_context nl)* '}' ;
```

Note: lists like `bounded_context_list` can be inlined or kept as separate rules; either way drop the `NEWLINE+` separator and rely on `nl` between items.

Apply the same pattern to: `domains_def`, `domain_block`, `actor_def`, `actors_def`, `actor_definition_list`, `arch`, `presentation_section`, `gateway_section`, `arch_component_list`, `exposure`, `exposure_properties`, `service_def`, `services_def`, `service_block_list`, `service_block`, `service_properties`.

**1.5 — Rewrite `use_case` body** keeping `NEWLINE+` as required:

```antlr
use_case : USE_CASE STRING '{' nl scenario* '}' ;
scenario : trigger action* ;
trigger
    : WHEN domain_name LISTENS quoted_event NEWLINE+
    | WHEN external_trigger                 NEWLINE+
    | WHEN quoted_event                     NEWLINE+
    ;
action
    : sync_action     NEWLINE+
    | async_action    NEWLINE+
    | return_action   NEWLINE+
    | internal_action NEWLINE+
    ;
```

**1.6 — Simplify `return_action` to a single alternative:**

```antlr
return_action
    : domain_name RETURNS (TO target=domain_name)? connector_word? phrase?
    ;
```

Delete the two-branch alternative that currently causes the "returns to X Y Z" ambiguity. Mark the `target=` label so the Go visitor can distinguish.

**1.7 — `actor_type` and `deployment_type` to `IDENTIFIER`:**

```antlr
actor_type      : IDENTIFIER ;
deployment_type : IDENTIFIER ;
```

**1.8 — `modifier` and `modifier_value`:**

```antlr
modifier : modifier_key (':' modifier_value)? ;
modifier_key   : IDENTIFIER ;
modifier_value : IDENTIFIER | STRING | NUMBER ;
```

**1.9 — `identifier` rule slim-down:** remove all structural keywords and the action verbs. Keep connectors and type-values:

```antlr
identifier
    : IDENTIFIER
    | USER | SYSTEM | SERVICE | CANARY | BLUE_GREEN | ROLLING
    | A | AN | THE | AS | TO | FROM | IN | ON | AT | FOR | WITH | BY | OF
    // NOTE: CONTEXTS/DATA_STORES/LANGUAGE/DEPLOYMENT previously appeared here;
    // remove per Q4 (they are structural keywords).
    ;
```

**1.10 — `phrase_word` drops `'when'` / `'use_case'`:**

```antlr
phrase_word : identifier | connector_word ;
```

**1.11 — Use the new keyword tokens in the productions** — e.g. `'arch'` → `ARCH`, `'when'` → `WHEN`, `'asks'` → `ASKS`, etc. Just a mechanical find-and-replace in the parser rules.

**Exit:** `make generate-grammar` succeeds without ANTLR warnings. If it reports ambiguities or left-recursion, fix before moving on.

## 8. Risks & mitigations

| Risk | Mitigation |
|---|---|
| ANTLR's LL(*) emits ambiguity warnings when `identifier` overlaps with connector/type tokens | Use ANTLR's `-Werror`/warning log; if warnings appear, inspect and decide case-by-case. Ambiguity between SERVICE-as-keyword and SERVICE-as-identifier is parser-context-disambiguated and should be warning-free. |
| Tree-sitter can't cleanly express "newlines significant in subtree" | Accepted: tree-sitter parses loosely inside use_case bodies; the authoritative parser is ANTLR/Go. The VS Code extension already calls into the Go server for semantic validation. |
| Downstream visitors hold implicit assumptions about AST shape | Full `go test ./...` plus example-corpus diffing catches regressions. Add new tests for each decision (see §6.3.5). |
| Breaking changes land in users' existing `.craft` files | Publish a migration note listing the reserved words. Run a scripted grep against known user repositories before tagging the release. |
| Regenerated parser renames token constants unexpectedly | ANTLR generates `CraftLexer<TOKEN>` constants deterministically from the lexer rule names. Choose rule names carefully (they're the ones listed in §4's lexer section) and don't rename them after first generation. |
